# 03. Document types, version 1

D3 converts the existing records instead of freezing them. A conversion needs a
target, so the types come first: which kinds of document exist, what each is typed
as, and how each existing document reaches its type.

## Principles

1. **One kind, one type, one home.** [MAP.md](../docs/MAP.md) already keeps one kind
   of knowledge in one place; the standard keeps that and gives each kind a type.
2. **Typed wherever a mistake can be made inexpressible.** Slipway's decision 4: a
   field is merged, required or narrowed until the wrong record does not compile.
   Prose stays prose inside the type.
3. **A conversion changes the carrier and never the reasoning.** Rule 1 of
   [RULES.md](../RULES.md) forbids rewriting a record. Text therefore moves byte for
   byte, generated by a converter rather than retyped, and a test compares it with
   its source before the source is deleted.
4. **Numbers survive.** Record 0026 becomes `a0026`, and the next decision is
   `a0044`. A number cited in code, commits and reviews goes on meaning the same
   record.
5. **A type Slipway lacks is prototyped here first**, and offered to Slipway only
   with the failure that needed it — Slipway's decision 7: a practice becomes a norm
   after a pilot needs it.
6. **Long prose may live in a Markdown body the record includes.** The record stays
   typed and referable, the body stays readable and renderable, and deleting the
   body breaks the build, because `include_str!` does.

Three of nerpa's types have no Slipway counterpart at all — proposal, review and

## A name two projects use differently

Slipway's `rfc!` is a **specification**: a goal, input and output contracts,
invariants. nerpa's RFC — like Rust's and the IETF's — is a **proposal**: measured,
designed, reviewed, and then turned into decisions. Version 1 calls them
specification and proposal and uses "RFC" for neither. Filed as F13.

nerpa's checks that stay after conversion, because the types do not hold them yet:
a cost is named; a supersession is mentioned by its successor; every section of the
architecture carries its marker; every link resolves; the book's joins agree.

The product's crates do not depend on the registry crate, so code goes on referring
to a record by text — `a0026` — and `cargo xtask docs` resolves every such mention,
as it resolves links today.

## Proposals

| Section of a nerpa RFC | Goes to |
| --- | --- |
| Summary, design, prior art, alternatives, costs | The proposal's body |
| What was measured | The proposal's body, each figure with its provenance |
| What is decided | Decision records, referenced from the proposal |
| Open questions | `Inquiry` work items, once scheduled |
| Review log, review history | One review record per round; every finding ends as a work item, a decision, or a stated rejection |
| Contract parts | A specification, whose `decided_by` names the decisions |
| Status: draft, in review, accepted, withdrawn | The proposal's status, as a variant |
| Touches | Typed references to decisions, invariants and observations |

## Invariants

The registry's shape is already right, and it becomes the type. `status` turns into
a variant, so that `Enforced` cannot be written without its adversarial tests and
`Unrepresentable` needs none; `enforced_by` and `tests` become anchors on the code
and on the test functions; `bypass` and `rationale` stay prose. Each `// ENFORCES:`
becomes a `#[doc_anchor]` with an id of its own, because anchor ids are unique
(F21).

## Local types

- Declared by macros in `doc/`, whose `build.rs` scans their directories
  into constants the way Slipway's scan does: one record per file, the file named by
  prefix and number.
- Each is introduced by a decision naming the failure that needed it.
- Each is retired when Slipway ships an equivalent: a decision supersedes the local
  one, and a work item converts its records.

Becomes: a decision on document types in `doc/`, one decision per local
type, and findings F13 to F17 and F21 in Slipway.
